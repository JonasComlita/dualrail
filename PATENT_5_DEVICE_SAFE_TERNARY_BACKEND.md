# System and Method for Device-Agnostic Ternary Lane Execution Using Shared Host and Device Backend Primitives

## Title

System and Method for Device-Agnostic Ternary Lane Execution Using Shared Host
and Device Backend Primitives

## Field

The disclosure relates to balanced ternary data processing, SIMD execution,
GPU kernels, CPU fallback execution, SYCL and CUDA programming, virtual-machine
backends, raw lane payload formats, and hardware-oriented arithmetic helpers
for field-programmable gate arrays and application-specific integrated
circuits.

## Background

Ternary values can be packed into binary host containers by encoding each trit
as a bit pair. Such lane encodings are useful for SIMD registers, GPU kernels,
wire-level FPGA interfaces, and transport buffers. However, different execution
targets commonly require different programming models. CPU scalar code, CPU
SIMD code, CUDA kernels, SYCL kernels, and hardware-oriented models may each
use different entry points, memory allocation APIs, and compilation rules.

If each backend separately implements the ternary lane arithmetic rules, the
implementations can diverge. A CPU reference path may handle invalid trit-pair
states differently from a GPU kernel. A SIMD path may normalize carry
differently from a scalar fallback. A hardware model may disagree with the
virtual-machine semantics. Maintaining separate implementations also increases
the cost of adding new lane widths or operations.

There is therefore a need for a shared backend layer in which the ternary lane
semantics are implemented once in a restricted, device-safe form and reused by
CPU fallback code, SIMD dispatch, CUDA launch wrappers, SYCL launch wrappers,
and hardware-oriented models.

## Summary

The disclosed architecture provides a device-agnostic ternary lane execution
backend. The backend operates on raw two-bit-per-trit lane payloads rather than
on host-only classes. The same low-level helper functions implement trit-pair
encoding, decoding, validity checks, invalid-lane generation, negation,
addition, subtraction, comparison, minimum, and maximum.

In one embodiment, the backend exposes raw 64-bit lane functions for lane
formats whose encoded payloads fit in 64 bits and raw two-limb 128-bit
functions for wider lane formats. The same helper functions are marked or
structured so that they can be compiled for both host and device code. The
helpers avoid standard-library containers, exceptions, strings, virtual
dispatch, dynamic allocation, and other host-only features in the kernel-callable
core.

In one embodiment, batch wrappers call the raw helpers over arrays of lane
payloads. Optional CUDA and SYCL launch wrappers invoke the same raw helpers
inside GPU kernels. CPU scalar and SIMD paths use the same semantic operations
as the device paths. Validation harnesses compare device outputs against CPU
reference outputs generated by the same disclosed lane semantics.

## Definitions

- **Trit pair:** a two-bit encoding of a balanced ternary trit.
- **Raw lane payload:** a binary integer payload containing packed trit pairs
  without host-only wrapper semantics.
- **Raw64 lane payload:** a raw lane payload stored in a 64-bit integer.
- **Raw128 lane payload:** a raw lane payload stored in a two-limb 128-bit
  structure.
- **Device-safe helper:** a function written in a restricted form suitable for
  compilation into CPU code and device kernels.
- **Invalid lane:** a lane payload containing invalid trit-pair states, uncleared
  padding bits, overflow carry, or otherwise invalid encoding.
- **Shared backend primitive:** a low-level operation implementing ternary lane
  semantics once for reuse by multiple execution backends.

## Detailed Description

### Raw Trit-Pair Encoding

In one embodiment, each ternary trit is encoded as a two-bit pair. Three of the
four possible bit-pair states encode negative, zero, and positive trits. The
remaining bit-pair state is reserved as invalid or spare. The backend provides
device-safe helpers to encode a trit into a pair, decode a pair into a trit,
test whether a pair is valid, and negate a pair.

The backend also validates that unused padding bits outside the active lane
width are clear. A raw payload with nonzero padding bits may be treated as
invalid.

### Raw64 and Raw128 Payload Families

In one embodiment, lane payloads containing up to 32 trits may be represented
inside a 64-bit integer. Wider payloads may use a two-limb raw structure:

```cpp
struct RawUInt128 {
    uint64_t lo;
    uint64_t hi;
};
```

The backend provides pair extraction, pair insertion, padding validation,
invalid-lane creation, and ternary operations for both raw64 and raw128
payloads. The two-limb structure avoids reliance on compiler-specific
`__int128` support in device code and keeps the raw payload ABI stable across
host and device compilers.

### Device-Safe Primitive Restrictions

In one embodiment, the backend primitives are written so that the same functions
can be compiled in host code and device code. The kernel-callable core avoids:

- standard-library containers;
- strings;
- exceptions;
- virtual dispatch;
- heap allocation;
- host-only reflection or runtime type systems; and
- backend-specific semantic branches.

The functions may be decorated with host/device annotations when compiled under
a device toolchain. In a plain C++ build, the same functions compile as ordinary
inline host functions.

### Ternary Lane Operations

In one embodiment, the shared primitives implement at least:

- lane validity checking;
- invalid-lane generation;
- tritwise negation;
- balanced ternary addition with carry;
- balanced ternary subtraction with borrow/carry normalization;
- comparison from most significant trit to least significant trit;
- lane minimum; and
- lane maximum.

Addition and subtraction decode corresponding trit pairs, apply carry, normalize
the intermediate sum into `{-1, 0, +1}`, and write an encoded trit pair to the
output. If final carry cannot be represented in the fixed lane width, the
operation returns an invalid lane payload.

Comparison returns a ternary comparison result that may be encoded as a one-trit
lane result. Minimum and maximum reuse the comparison primitive and return one
of the original valid lane payloads.

### Batch Wrapper Layer

In one embodiment, a batch wrapper layer applies the raw lane primitives over
arrays:

```text
batchTritwiseAddRaw64(a, b, out, count, trits)
batchTritwiseAddRaw128(a, b, out, count, trits)
```

The batch wrapper is itself device-safe and can be used as a scalar reference
loop, a CPU fallback loop, or the body of a larger kernel. The wrapper operates
on raw pointers to input and output arrays and therefore does not depend on
host-only lane classes.

### CUDA and SYCL Launch Wrappers

In one embodiment, optional CUDA launch wrappers create GPU kernels that map a
thread index to an array element and call the same raw lane primitive used by
the CPU path. In another embodiment, optional SYCL launch wrappers submit
parallel kernels that call the same raw lane primitive. These wrappers are
enabled only when the corresponding toolchain macro is present, leaving ordinary
builds free of CUDA or SYCL dependencies.

The kernel launch wrappers do not redefine the ternary operation. They expose a
backend-specific launch mechanism around the shared raw primitive.

### CPU SIMD and Scalar Backend Selection

In one embodiment, CPU batch APIs provide a scalar reference backend, an
automatic backend selector, and optional SIMD acceleration. Optimized SIMD paths
may be provided for selected lane widths and operations. When the optimized path
is not available or not selected, execution falls back to the scalar reference
path. The optimized path and scalar path are validated against the same
underlying lane semantics.

### Device Memory Allocation

In one embodiment, a virtual-machine state allocator abstraction allows the same
VM state shape to be backed by host memory, CUDA managed memory, or SYCL shared
USM memory. Device-specific allocator implementations are optional and are
enabled only when compiled with the corresponding device backend.

This allocator layer is not required for all raw lane kernels, but it allows
the same VM state model to move toward GPU or heterogeneous execution without
changing the machine-state layout.

### Validation and Tuning

In one embodiment, a shared validation harness generates deterministic raw lane
input corpora, including valid payloads, invalid trit-pair states, and invalid
padding-bit cases. The harness computes expected CPU results using the same raw
lane semantics and compares CUDA or SYCL kernel results against the expected
outputs. Timing, checksum, backend name, device name, compiler, operation,
width, count, and launch geometry may be written to a tuning-results log.

## Example Operations

### Raw64 Add

```cpp
out[i] = addLane64(a[i], b[i], trits);
```

The function validates both raw lane payloads, performs balanced ternary
addition with carry across trit pairs, and returns an invalid payload if the
result cannot fit.

### Raw128 Negation

```cpp
out[i] = negLane128(in[i], trits);
```

The function validates the two-limb raw payload and flips each valid trit pair.

### CUDA Launch Wrapper

```cpp
cudaLaunchTritwiseAddRaw64(a, b, out, count, trits, blockSize, stream);
```

The launch wrapper invokes a CUDA kernel that calls the same raw add primitive
used by host code.

### SYCL Launch Wrapper

```cpp
syclLaunchTritwiseAddRaw128(queue, a, b, out, count, trits, localSize);
```

The launch wrapper submits a SYCL kernel that calls the same raw add primitive
used by host code.

## Advantages

Embodiments of the disclosed architecture may provide one or more of the
following technical advantages:

- Implements ternary lane semantics once and reuses them across host and device
  targets.
- Reduces semantic drift between scalar reference, CPU SIMD, CUDA, SYCL, and
  hardware-oriented models.
- Allows ordinary builds to avoid CUDA and SYCL dependencies.
- Enables raw lane kernels without pulling host-only classes into device code.
- Supports multiple lane widths through a shared trit-count parameter.
- Handles invalid trit-pair states and padding-bit violations consistently.
- Provides a stable two-limb raw 128-bit payload for wide lane formats without
  relying on compiler-specific 128-bit integers in device code.
- Provides deterministic validation and tuning records across backends.
- Prepares the same lane ALU semantics for FPGA and ASIC translation.

## Abstract

A device-agnostic ternary lane execution backend operates on raw
two-bit-per-trit payloads. Shared host/device primitive functions validate raw
lane payloads, decode trit pairs, perform balanced ternary operations, and
encode output payloads. The primitives support raw 64-bit payloads and two-limb
128-bit payloads and implement operations including negation, addition,
subtraction, comparison, minimum, and maximum. Batch wrappers apply the same
primitive semantics to arrays, while optional CUDA and SYCL launch wrappers call
the same primitives inside device kernels. The architecture avoids redefining
ternary semantics for each backend and provides consistent scalar, SIMD, GPU,
and hardware-oriented behavior.
