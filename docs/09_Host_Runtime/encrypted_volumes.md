# Encrypted volumes (selected host-only TRITENC1 policy)

Production support is host-only `TRITENC1` AES-256-GCM. The ternary-native
encrypted-volume proposal is explicitly non-selected. `TRITENC1` is not a new
guest filesystem and is not accepted directly by the VM block-device loader;
the existing loader continues to consume canonical tDisk v2.

## Host-compatible envelope (implemented, explicit opt-in)

`encrypted_volume_host.h` owns a small, little-endian envelope for opaque image
bytes.  A canonical tDisk v2 file can be encrypted as a whole, then decrypted
to a normal `.tdisk` path before `attachBlockBackingFile` is called.  The
module does not mount the encrypted envelope directly and does not rewrite the
decrypted image.  It does, however, validate the complete canonical tDisk v2
header, record geometry, raw T40 words, ordering, and FNV-1a checksum at both
image boundaries.  The runtime remains the final loader and persistence
authority.

The envelope header is 64 bytes:

| field | type | meaning |
|---|---|---|
| magic | 8 bytes | `TRITENC1` |
| version | u32 | `1` |
| algorithm | u32 | `1` = AES-256-GCM; test-only IDs are never production formats |
| header bytes | u32 | `64` |
| flags | u32 | reserved; must be zero |
| chunk bytes | u32 | 4 KiB..1 MiB, default 64 KiB |
| logical block words | u32 | optional metadata (`27` for current tDisk), validated when nonzero |
| logical size | u64 | plaintext byte count |
| logical block count | u64 | derived when block metadata is present |
| chunk count | u64 | at most `2^24`; exact ceiling of logical size/chunk size |
| nonce prefix | 8 bytes | nonzero prefix generated by the production provider CSPRNG |

Each chunk stores `chunk_index`, plaintext/ciphertext byte counts, a 16-byte
GCM tag, and ciphertext.  The authenticated data is the exact header plus the
chunk metadata.  A 12-byte nonce is `nonce_prefix || little_endian(index)`;
production callers cannot supply or select the prefix; the provider owns
generation because TRITENC1 has no caller-managed nonce-reuse registry.  The
host accepts
4 KiB..1 MiB chunks, logical plaintext up to 1 TiB, and envelope input up to
the corresponding bounded framing size.  It rejects unknown algorithms,
nonzero flags, all-zero prefixes, count/size overflow, non-contiguous chunks,
non-final short chunks, AAD-size mismatches, truncation, trailing bytes, and
provider/key/tag/nonce mismatches before plaintext is returned.  A zero-byte
opaque payload is rejected because a header-only TRITENC1 envelope has no GCM
record through which to authenticate its header; canonical tDisk v2 images
always include their 36-byte header.  Failed decryptions cleanse staged
plaintext and intermediate buffers.

The key-file helper is intentionally strict: `readKeyFile` and
`readAes256KeyFile` accept only a regular file containing exactly 32 raw bytes
or exactly 64 hexadecimal characters (upper- or lower-case).  Base64, UTF-8
text, newline-terminated values, short files, long files, non-hex 64-byte
values, and directories are rejected.  Key bytes are never included in
returned error text.  Callers remain responsible for protecting the key file
and for clearing the returned key when the operation is complete.

The canonical tDisk boundary is the v2 format described in
`image_format.md`: a 36-byte header, nonzero generation, nonnegative sorted
unique block indices within the 64 GiB host geometry, at most `2^24` records,
valid raw T40 words, no all-zero records, exact record-area length, and the
header checksum over the exact little-endian records.  This is a host-side
preflight check; it is not a replacement for the production runtime loader.

Production encryption uses only the optional `OpenSslAes256GcmProvider` in
`encrypted_volume_openssl.cpp`.  It fetches `AES-256-GCM` through the OpenSSL 3
EVP provider boundary, uses `RAND_bytes` for nonce prefixes, clears the
OpenSSL error queue, and returns fixed redacted errors.  If the translation
unit is built without `TRIT_ENCRYPTED_VOLUME_ENABLE_OPENSSL`, or if the
provider/cipher cannot be fetched, the provider fails closed.  There is no
fallback cipher or unauthenticated mode.

File promotion writes beside the destination using exclusive creation and
owner-only temporary permissions (POSIX `0600`; a non-inheriting owner/system
ACL on Windows), flushes the temporary file, durably syncs the POSIX parent
directory after rename, and uses one atomic replacement operation.  The previous
copy-overwrite fallback is deliberately absent: if
promotion fails, the destination is left alone and the temporary ciphertext or
plaintext file is removed.  Decryption stages plaintext in memory, and any
output temporary is removed on every normal failure path.  Encrypted-volume
errors do not include paths, key bytes, ciphertext, nonce prefixes,
OpenSSL error-queue details, or provider-supplied diagnostic text.

Current development hosts have OpenSSL 3.6 under `C:/msys64/ucrt64`
(`pkg-config --cflags --libs openssl`).  The repository's default CMake cache
keeps `TRIT_ENCRYPTED_VOLUME_OPENSSL=OFF`; the existing CMake target therefore
exercises the fail-closed/mock path unless explicitly configured otherwise.

Focused validation, including the CMake-wired parser test, is:


The main test covers OpenSSL and a clearly marked deterministic mock (test-only):
AES-256-GCM known-answer and randomized multi-chunk vectors, round-trip,
wrong-key rejection, ciphertext/header tamper, chunk reorder, truncation,

## Production lifecycle and commands

The supported lifecycle is encryption at rest:

1. Validate the envelope with `volume inspect`.
2. Decrypt it into a restricted, exclusively-created temporary plaintext file.
3. Set `TRIT_VOLUME_PLAINTEXT` for the explicitly managed host command.
4. Clear the environment, detach, and re-encrypt to a new temporary envelope.
5. Atomically replace the destination and remove the plaintext temporary.

The stable CLI is exposed through `python tools/trit_tool.py volume` and the
portable `trit_volume` target:

```powershell
python tools/trit_tool.py volume inspect --json volume.tenc
python tools/trit_tool.py volume encrypt --key-file key.bin image.tdisk volume.tenc
python tools/trit_tool.py volume decrypt --key-file key.bin volume.tenc image.tdisk
python tools/trit_tool.py volume attach/run --key-file key.bin volume.tenc -- host-command --arg
```

Mutation commands require a key file containing exactly 32 raw bytes or 64 hex
characters. Key material is never accepted as an argument, environment value,
manifest field, or diagnostic. OpenSSL is optional at build time; when it is
not linked, mutation requests fail closed while header-only inspection remains
available. `--overwrite` is required before replacing an existing destination.

Secure deletion of a plaintext temporary cannot be guaranteed on SSDs or
copy-on-write filesystems. Deployments requiring no plaintext-at-rest mount
must wait for a future authenticated block adapter/format. The current host
consumer preserves the old envelope on failed re-encryption, durably promotes
successful POSIX replacements, and cleans its managed temporary on normal exit
and handled failure. An abrupt process or host crash can still leave a
plaintext temporary behind; deployments must use restricted temporary storage
and an external recovery/cleanup procedure.

## Independent review and release status

The selected TRITENC1 provider, parser, and lifecycle have focused tests, but
the host-volume roadmap gap is not closed until the independent review has no
unresolved high-severity findings. Review scope includes AAD coverage, nonce
counter uniqueness, chunk ordering, tamper/replay/truncation behavior, random
failure handling, atomic replacement/crash consistency, key lifetime, OpenSSL
EVP usage, and parser fuzz bounds. Format-affecting remediation requires a new
envelope version rather than silently changing TRITENC1.

The default CMake cache keeps `TRIT_ENCRYPTED_VOLUME_OPENSSL=OFF`; production
deployments must explicitly enable OpenSSL 3.x and provide the key provider.
Focused validation can be run with:

```powershell
cmake -S . -B build -G Ninja `
  -DTRIT_ENCRYPTED_VOLUME_OPENSSL=ON `
  -DOPENSSL_ROOT_DIR=C:/msys64/ucrt64
cmake --build build --target test_encrypted_volume
ctest --test-dir build -R '^test_encrypted_volume$' --output-on-failure
```

The CMake target also builds the host consumer `trit_volume`; OpenSSL must be
enabled on the configuration used for mutation commands. The operation keeps
the key outside guest metadata and removes the managed decrypted file according
to the lifecycle above.

## Ternary-native format (proposal; not selected)

The guest storage contract remains unencrypted tDisk v2.  A future native
format should not reuse the host envelope or the current `ternary_montgomery.h`
candidate as an implicit cipher.  Before selection, cryptographic review must
freeze a new format version and a provider backed by reviewed primitives.

The proposed `TENC-TN/1` layout is:

1. A fixed little-endian header with magic, version, profile/algorithm ID,
   logical block geometry, key-slot/KDF descriptor, random volume nonce, and a
   header hash.  Unknown versions and algorithms fail closed.
2. A domain-separated metadata authentication record (`"trit.tenc.tn1.meta"`)
   followed by one authenticated record per logical block.  The record AAD
   includes version, volume UUID, block index, plaintext length, and generation;
   no record may be accepted under a different domain.
3. Per-block nonces are derived from a unique volume nonce and the block index
   (with an explicit generation counter for rewrites).  Nonce reuse, counter
   wrap, and rollback are hard errors.  Tags are fixed-size and verified before
   a block is exposed to VFS/WAL recovery.
4. Key slots carry only wrapped data keys and KDF parameters; raw keys never
   appear in logs, manifests, diagnostics, or guest-visible metadata.  Key
   rotation writes a new version and re-authenticates all metadata before the
   old slot is retired.

This design is deliberately a review boundary: it has no guest mount hook,
no kernel ABI, and no release-image selection.  A cryptographic review must
decide the AEAD/KDF, nonce derivation, rollback policy, recovery ordering, and
constant-time implementation before a `TENC-TN/1` record can become a guest
storage contract.
