# Query-corpus review findings: Q001-Q034

## Review scope

This review covers the 34 Trit/TCL/OS3 questions in `questions/Q001-Q034.json`.
The corpus was checked against the current generated public snapshot:

- Snapshot commit: `37fd0da68e764f3755485f6906c6c859ebb6e496`
- Snapshot generated at: `2026-08-12T22:26:36-07:00`
- Snapshot source declaration: `root registries, TEST_MANIFEST.json, and tracked source paths`

The questions intentionally require repository-specific terms (Trit v2, TCL,
VM, IMEM/DMEM, CSRs, TASM, and SSA) and reject generic ternary-computing
answers. No source or snapshot files were changed during this review.

## Findings

### F-001 — Snapshot relation metadata has commit skew (medium retrieval risk)

The snapshot declares commit `37fd0da68e764f3755485f6906c6c859ebb6e496`, and
its `sources`, `symbols`, and `tests` records use that commit. However, 63
stack-node/component source references and 54 contract source references still
cite the short historical commit `d168bc8`.

Exact evidence:

- `treatcode/public/api/v1/snapshot.json`: `snapshot.commit` is
  `37fd0da68e764f3755485f6906c6c859ebb6e496`.
- The `tc:layer:phase-00-authority` source refs for `AGENTS.md`,
  `TEST_MANIFEST.json`, and `tools/trit_tool.py` cite `d168bc8`, while its
  evidence ref cites the current snapshot commit.
- `tc:component:low-level-ir-ternary-ir-h` likewise cites `d168bc8` for
  `ternary_ir.h` while the source record is evidence-linked to the current
  snapshot commit.

Impact: relation answers can expose an older commit URL or mix historical and
current evidence. Q001-Q003, Q032-Q034, and any relation-mode test should check
that the answer reports the path and current behavior rather than treating the
old commit reference as a second implementation.

### F-002 — GPU implementation is present locally but absent from the public index (high retrieval risk)

The repository has concrete optional CUDA/SYCL headers and a validation corpus,
but the generated public snapshot has no `sources`, `components`, or `symbols`
whose `path` is `ternary_gpu_kernels.h` or `ternary_gpu_validation.h`.

Exact evidence:

- `ternary_gpu_kernels.h` contains `TERNARY_ENABLE_CUDA`,
  `TERNARY_ENABLE_SYCL`, and `cudaTritwiseNegRaw64Kernel`.
- `ternary_gpu_validation.h` enumerates `Neg`, `Add`, `Sub`, `Compare`, `Min`,
  and `Max` over lane cases `L1`, `L5`, `L10`, `L20`, `L40`, and `L50`, with
  CPU-reference/checksum records.
- `TEST_MANIFEST.json:157-167` declares the manual `accelerators` suite,
  `test_cuda_kernels`, `test_sycl_kernels`, and the `ENABLE_CUDA=ON` /
  `ENABLE_SYCL=ON` requirements.
- A snapshot path query returns zero source, component, and symbol records for
  both GPU headers.

Impact: Q020 can verify that retrieval does not claim “no GPU support,” but a
semantic search over only public entities cannot currently return the concrete
kernel symbols. The index should eventually add these paths or explicitly
surface the omission as a known coverage gap.

### F-003 — Current SSA compiler source is not the indexed low-level IR source (high retrieval risk)

The current compiler documentation and source describe structural SSA in
`ternary_compiler_ir.h`, while the public snapshot indexes the older minimal
lowering header `ternary_ir.h`.

Exact evidence:

- `docs/05_Compiler_Infra/ternary_ir.md:3` says `Source of truth:
  ternary_compiler_ir.h`; lines 179-188 describe SSA lowering, allocation,
  object emission, and linking through that file.
- `ternary_compiler_ir.h:1` identifies itself as “Structural SSA IR,” and
  lines 16-26 define `ValueId` and the `Effect` enum; lines 70-99 define
  `Instr` and `Branch3`; lines 141-188 define `AllocationResult`,
  `ObjectModule`, and `CompileResult`.
- `ternary_ir.h:2-6` instead describes a “minimal typed IR lowering to
  existing ternary assembly.”
- `treatcode/public/api/v1/snapshot.json` has
  `tc:component:low-level-ir-ternary-ir-h` with path `ternary_ir.h`, but zero
  source/component/symbol records for `ternary_compiler_ir.h`.

Impact: Q032-Q034 are designed to expose answers that cite the wrong IR. A
retrieval result that describes only `sandbox::ir::Program` is stale for the
current TCL compiler pipeline; a result about `AllocationResult` and
`allow_ast_replay` must cite the current compiler header even though that path
is not yet a public entity.

### F-004 — VM CSR count in the execution note omits v2 extension IDs (medium factual risk)

The VM-state note says “47 CSR slots (indices 0–46),” but the current ISA and
architecture manifest extend the CSR space through ASID.

Exact evidence:

- `docs/03_Execution_Engine/vm_state.md:88` states `47 CSR slots (indices
  0–46)`.
- `ternary_isa.h:675-681` defines `CSR_POWER_CONTROL = 47`, then
  `CSR_ISA_VERSION`, `CSR_ISA_FEATURES`, `CSR_MMU_BASE_PAGE_WORDS`,
  `CSR_MMU_SUPERPAGE_WORDS`, `CSR_ASID`, and `CSR_MAX_ID = CSR_ASID`.
- `ARCHITECTURE_MANIFEST.json:170-175` assigns v2 extension IDs 48 through 52.

Impact: Q015 should require both the base/device map and v2 extension CSRs.
The website must not answer “only 0–46 exist” as if that were the complete
current Trit v2 CSR contract; the note needs clarification in a later repair.

### F-005 — Planned ternary-native text encodings must not be presented as current TCL/OS3 ABI (medium retrieval risk)

The public snapshot includes future TASCII-81/base-27/base-81 entities, but
they are explicitly planned proposals rather than current guest ABI.

Exact evidence:

- `tc:capability:capability-encoding-tascii81-ternary-native` and
  `tc:capability:capability-encoding-base27-base81-dumps-ternary-native` have
  `status: "planned"`, `maturity_status: "specified"`, and
  `evidence_status: "planned"`.
- `tc:decision:trit-decision-tascii81-not-abi` says ternary-native symbolic
  encodings are proposals, not guest ABI, and has `disposition: "open"`.
- `TEST_MANIFEST.json:136-154` marks the `symbolic_encodings` suite as
  planned with no targets.

Impact: generic answers about “the ternary text format” can be accidentally
promoted to current TCL/OS3 behavior. The Q001/Q003 authority questions and
the `forbidden_generic_claims` fields should be used to ensure planned
notation is labeled planned and not substituted for TASM, TritWord27, or the
runtime syscall ABI.

### F-006 — Historical OS3 freeze records are intentionally retained but are not current truth (medium retrieval risk)

The public index retains OS3 Phase 4 history, including missing historical
paths, alongside the accepted Trit v2 contract.

Exact evidence:

- `tc:decision:trit-decision-v2-over-os3-freeze` is canonical/accepted and
  states that checked-in v2 manifests and implementation define current widths,
  ABI versions, and image readers.
- `tc:decision:trit-decision-historical-os3-freeze` is non-canonical/rejected;
  its `OS3/PHASE4_COMPLETION_ROADMAP.md` source ref has `status: "missing"`.
- Snapshot source records for `OS3/PHASE4_COMPLETION_ROADMAP.md`,
  `OS3/minimal_kernel_bringup.tasm`, and `OS3/strategic_architecture.md` are
  marked `status: "missing"`; those paths are not present in the working tree.

Impact: a query mentioning OS3 can retrieve historical prose without making it
clear that current v2/TCL behavior supersedes it. Retrieval validation should
surface the accepted v2 entity and mark the OS3 freeze as historical/rejected.
