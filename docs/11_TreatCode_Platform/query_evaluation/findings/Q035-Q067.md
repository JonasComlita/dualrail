# Query evaluation findings: Q035–Q067

## Review scope

Reviewed the current Trit/TCL/OS3-adjacent source files and the regenerated
`treatcode/public/api/v1/snapshot.json` before editing. The shard covers 33
questions (Q035–Q067): TCL language and diagnostics; the host compiler's
lexer/parser/AST/type inference/SSA/optimization/allocation/codegen/linking;
self-hosted TCL frontend/backend; runtime and SDK; reset/boot/trap artifacts;
and kernel HAL, MMU/process, scheduler, syscall, and IPC boundaries.

## Findings and retrieval risks

1. **Exact compiler/TCL component-index gap.** The files
   `tcl_lexer.trit`, `tcl_ast.trit`, `tcl_type.trit`, `tcl_infer.trit`,
   `tcl_ir.trit`, `ternary_compiler_lexer.h`, `ternary_compiler_parser.h`,
   `ternary_compiler_ast.h`, `ternary_compiler_types.h`, and
   `ternary_compiler_ir.h` now appear in the regenerated snapshot's
   `sources`, but still have no corresponding `components` entries. A query
   that expects component-level navigation for one of these paths will miss
   even though source-backed retrieval can succeed. The questions therefore
   cite the indexed umbrella/current components (`ternary_compiler.h`,
   `ternary_compiler_codegen.h`, `tcl_parser.trit`, and `tcl_frontend.trit`)
   and use source IDs only where the snapshot exposes no component.

2. **Exact stale path in boot prose.** `native_kernel_boot.tasm:3` says it is
   assembled before `OS3/native_kernel_trap_stub.tasm`, but the authoritative
   file in this checkout is `native_kernel_trap_stub.tasm` at repository root.
   The three `OS3/...` paths (`OS3/PHASE4_COMPLETION_ROADMAP.md`,
   `OS3/minimal_kernel_bringup.tasm`, and `OS3/strategic_architecture.md`) are
   also present as snapshot source records but do not exist on disk. This can
   cause a query to retrieve a historical OS3 citation as if it were current.
   I did not change boot or snapshot sources per task ownership; Q060–Q063 use
   existing root-level TASM paths and explicitly distinguish diagnostic
   bring-up from production boot.

3. **TASM symbol coverage is partial but improved.** The regenerated snapshot
   now exposes label symbols for `native_trap_entry`, `bringup_entry`,
   `write_trap`, `fsync_trap`, and `timer_trap`; however, instruction-level
   operands and constants such as `syscall 16` and `DTB_MMU_ENABLE` remain only
   source terms. Boot questions retain component/source expectations and use
   required terms for those instruction-level facts rather than assuming every
   assembly token is a symbol entity.

4. **Kernel syscall constant coverage gap.** `kernel.trit` defines and uses
   `KCAUSE_SYSCALL` (definition at line 96 and dispatch use around line 8698),
   yet the snapshot does not expose a `KCAUSE_SYSCALL` symbol entity. Q067
   intentionally expects the indexed kernel component and named state-slot
   symbols while retaining `KCAUSE_SYSCALL` as a required source term. This is
   a retrieval risk for exact syscall-cause queries.

5. **Generated symbol-ID volatility.** Regeneration changed numeric suffixes
   for host-codegen IDs (for example, `TypeInferencer` is currently
   `tc:symbol:ternary-compiler-codegen-h-typeinferencer-21`, and
   `rewriteAssemblyLine` is `...-821`). The shard was repaired against the
   current snapshot, but a future line-order regeneration may change these
   suffixes. The public API should provide stable symbol identities or the
   question fixture generator should resolve IDs by `(path, symbol, span)`.

## Repair applied

- Created `questions/Q035-Q067.json` as a top-level array with exactly 33
  contiguous, distinct question records.
- Added all required per-record fields: `id`, `question`, `query`, `mode`,
  `expected_entity_ids`, `expected_source_paths`, `required_terms`,
  `forbidden_generic_claims`, and `rationale`.
- Repaired host-codegen entity IDs after the current snapshot regeneration.
- Tuned query modes to the public search contract: natural-language prompts
  use semantic search, literal paths use exact search, and symbol prompts use
  one concrete symbol string. This avoids false negatives from treating a
  multi-term sentence as an exact relation or symbol lookup.
- Created this findings file; no shared retrieval, source, manifest, or kernel
  files were edited.
